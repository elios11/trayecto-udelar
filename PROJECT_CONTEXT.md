# Contexto compartido del proyecto

Este documento contiene el contexto estable que todos los chats deben conocer. No es un backlog ni una especificacion de una funcionalidad concreta. Las reglas operativas para los agentes estan en `AGENTS.md`.

## Producto

- El producto se llama **Trayecto** y ayuda a estudiantes de Udelar a explorar su curricula, registrar avance y planificar materias.
- La experiencia debe ser clara para estudiantes, funcionar con teclado y tactil, y adaptarse a escritorio y movil.
- La interfaz y los textos destinados a las personas usuarias se mantienen en espanol, salvo una solicitud explicita distinta.
- La informacion curricular debe conservar su trazabilidad. No se deben presentar supuestos, sugerencias o datos incompletos como si fueran informacion institucional confirmada.
- La auditoría del plan y la auditoría de su catálogo son estados independientes. Una materia sólo integra la malla, el buscador y el planificador normales cuando una fuente curricular oficial vigente respalda exactamente su inclusión; la composición de Bedelías por sí sola se conserva como candidata recuperable, no como catálogo vigente.

## Alcance y datos actuales

- Bedelías inventaría 184 identidades canónicas como vigentes de grado, tecnicatura, tecnólogo y CIO. Las auditorías resolvieron falsos vigentes, títulos históricos convertidos o aliases administrativos y excluyen 38 identidades del selector. Ocho IDs de plan se mantienen curados —siete vigentes y Computación Plan 1997 histórico— y otros 139 se generan desde snapshots y auditorías; 177 identidades canónicas ya tienen evidencia oficial cerrada y la cola de contraste quedó vacía. En las 139 proyecciones generadas, 63 catálogos quedaron verificados, 64 son parciales y 12 conservan sólo la estructura del plan: todos siguen seleccionables, pero únicamente publican materias respaldadas.
- Los datos consumidos por la interfaz estan en `app/data/`. Las transformaciones y fuentes asociadas viven en `data/`, `scripts/` y `docs/bedelias-importer.md` cuando corresponde.
- El inventario global vigente de Bedelías se genera de forma secuencial y reanudable con `npm run bedelias:inventory -- --types "GRADO|TECNICATURA|CIO" --dry-run`; sus índices por servicio viven en `data/bedelias/services/` y el manifiesto académico en `data/bedelias/inventory/global-current.json`. `scripts/build-extracted-academic-plans.mjs` proyecta de forma determinista las identidades pendientes habilitadas explícitamente por este producto y conserva sus estados, anomalías y elegibilidad de publicación en `data/bedelias/inventory/ui-extracted-plans.json`.
- La proyección clasifica por plan cada entrada como `verified`, `candidate`, `historical-equivalent`, `administrative` o `rejected`, y registra procedencia separada para inclusión, nombre y créditos. Sólo `verified` se publica en el catálogo normal. Los candidatos, asientos administrativos y aliases permanecen en los artefactos para auditoría, importaciones y recuperación, pero no suman ni aparecen como materias vigentes. Las materias parecidas no se fusionan por texto aislado: una variante se consolida únicamente dentro de un grupo oficial de alternativas de una materia, con identidad, carga y asignación coincidentes. Toda materia enumerada explícitamente en los períodos de una trayectoria oficial debe conservar al menos una identidad canónica visible en Currícula; una prueba global bloquea cualquier regeneración que la pierda.
- Para todo plan, la trayectoria predeterminada de Currícula debe reproducir la malla, grilla, damero o trayectoria sugerida oficial vigente que publique el servicio, incluidos sus períodos, bloques flexibles y perfiles. Las áreas se conservan como asignaciones y requisitos, no sustituyen los semestres u otros períodos publicados. Ningún plan seleccionable puede quedar sin períodos que contengan materias reales: cuando la trayectoria oficial todavía no esté reconciliada o se haya documentado que no existe, la interfaz debe construir desde la composición de Bedelías un `Recorrido orientativo generado`, claramente provisional y sin atribuirlo a la institución; debe conservar las materias y opciones disponibles, explicar la procedencia y ser reemplazado por la trayectoria oficial en cuanto se verifique. Marcadores administrativos, validaciones finales o bloques vacíos no satisfacen esta garantía por sí solos. - El contrato portable `trayecto-personal-data` v4 vive en `app/personal-data.mjs`, y `app/personal-data-migration.mjs` concentra la hidratación, migración y compatibilidad. `formatVersion`, la revisión concurrente y la revisión curricular son conceptos separados; una versión futura nunca se reinterpreta ni se sobrescribe. Cada perfil conserva un `academicHistory` personal trazable: curso aprobado proyecta `approved`, mientras exoneración, examen aprobado y acreditación proyectan `exonerated`; `progress` se mantiene como proyección materializada y debe coincidir con esa historia antes de persistir. Corregir, anular o restaurar agrega una revisión y nunca modifica la currícula ni simula una escolaridad oficial. Los perfiles con el mismo `progressPlanId` comparten la secuencia canónica; los demás aíslan IDs aun si coinciden sus materias. Las bolsas JSON `extensions` con namespace se preservan aunque el cliente no las comprenda, mientras cualquier semántica obligatoria exige una nueva versión. Cada perfil lleva una revisión curricular trazable; materias retiradas o sin equivalencia oficial permanecen históricas, restaurables y exportables sin acreditar automáticamente. La política completa está en `docs/personal-data-compatibility.md`. La frontera con React transporta `activeProfileId` y `activeScenarioId`: perfiles que comparten plan conservan identidades separadas, sólo comparten progreso e historial cuando usan el mismo `progressPlanId`, y los escenarios no activos o archivados no se reconstruyen ni se sobrescriben. Las operaciones de escenarios confirman primero la edición visible sobre v4, escriben el cambio estructural con las garantías de revisión y conflicto existentes y recién entonces hidratan el escenario elegido; progreso e historial permanecen compartidos por el perfil. Una selección antigua ambigua bloquea el guardado en lugar de fusionar datos. La exportación completa se genera desde el estado vigente en memoria e incluye todos los perfiles y escenarios locales en v4, incluso si el último guardado falló. La importación explícita sigue aceptando las formas completas v1/v2/v3 y el planificador v1, pero rechaza íntegramente cualquier archivo cuya migración descartaría fragmentos; la recuperación automática del almacenamiento heredado continúa siendo tolerante. El formato separado del planificador se mantiene en v1, representa únicamente el escenario activo y no incluye historial.
- Escenarios y línea temporal permanecen en el contrato portable y en sus módulos de dominio para conservar compatibilidad, exportaciones y datos existentes, pero no se exponen en la interfaz principal. El planificador muestra directamente los semestres del escenario activo y evita las etiquetas `Plan principal`, `Escenario` y `Línea temporal`; importar un planificador sigue sustituyendo sólo ese contenedor sin tocar otros escenarios guardados.
- Cada documento v4 conserva snapshots curriculares compactos y compartidos por plan y revisión dentro de la extensión `org.trayecto.curriculumSnapshots`. Cuando la revisión publicada cambia, Trayecto compara identidades, cargas, áreas, requisitos y credenciales sin inferir equivalencias por semejanza: sólo un alias oficial trazable puede resolver otra identidad. El aviso puede descartarse únicamente para ese par de revisiones; adoptar una revisión exige una comparación no bloqueante, crea antes una instantánea local y nunca reemplaza IDs del historial. Si falta la referencia histórica o una materia personal queda sin equivalencia, la adopción permanece bloqueada y los datos anteriores siguen exportables.
- El repositorio público se audita con `npm run security:repo`; CI usa permisos de solo lectura y Dependabot mantiene npm y GitHub Actions sin auto-merge. `SECURITY.md` es el canal de divulgación responsable y las exportaciones de progreso se consideran información académica personal.
- Dos planes oficialmente articulados pueden declarar un plan canónico de progreso compartido cuando sus materias usan identificadores compatibles. Esto permite alternar entre un título intermedio y su continuación sin duplicar aprobaciones, manteniendo por separado sedes, recorridos, mínimos y credenciales de cada plan.

## Arquitectura

- El repositorio canónico público es <https://github.com/elios11/trayecto-udelar>; `main` es su rama principal y el remoto local se llama `origin`.
- Aplicacion web con React 19, TypeScript, vinext y Vite.
- El codigo principal de la interfaz esta bajo `app/`; `app/page.tsx` contiene actualmente gran parte del estado y la interaccion, y `app/globals.css` contiene los estilos globales.
- La jerarquía de facultades, carreras y planes vive en `app/academic-catalog.ts`, que combina el núcleo curado con `app/data/extracted-academic-catalog.json`; los registros de estado por plan se inicializan desde ese catálogo. Los datasets masivos se registran para carga diferida mediante `app/data/extracted-academic-loaders.ts` y `app/academic-plan-registry.ts`, sin condicionales por carrera en la interfaz central. Una composición no publicada mantiene la carrera seleccionable y muestra un estado vacío explícito, sin inventar materias o mínimos.
- Las pruebas automatizadas estan bajo `tests/` y se ejecutan con el runner nativo de Node despues de la compilacion.
- El proyecto usa npm y requiere Node.js `>=22.13.0`. Desde un clon limpio, `npm ci`, `npm run verify` y `npm run package` reconstruyen, prueban y empaquetan el artefacto portable en `outputs/portable/`; su manifiesto determinista se verifica con `node scripts/package-portable-build.mjs --verify`.
- El despliegue está separado de CI y del empaquetado portable. `.openai/hosting.json` configura Sites como adaptador actual, pero el workflow sólo verifica, compila y conserva el artefacto sin desplegar ni usar secretos.

## Decisiones de producto transversales

- Preservar los datos y el progreso existentes al introducir nuevas preferencias o formatos de almacenamiento. Toda migracion debe ser compatible hacia atras o incluir una estrategia explicita.
- Las preferencias personales sin requisito de sincronizacion remota se guardan localmente en el navegador.
- Evitar dependencia estructural de un proveedor: el repositorio y los formatos exportables son la fuente portable, el dominio propio no debe depender del host, y cualquier persistencia remota debe usar contratos estandar, migraciones reproducibles y un procedimiento probado de exportacion y restauracion. Sites puede alojar la aplicacion, pero sus servicios propietarios no deben ser la unica forma de ejecutar, autenticar o recuperar Trayecto.
- No introducir autenticacion, base de datos, telemetria ni servicios externos solo por conveniencia de implementacion; requieren una decision de producto explicita.
- Mantener accesibilidad, contraste suficiente, estados de foco, navegacion por teclado, soporte tactil y respeto por `prefers-reduced-motion`.
- Evitar que una funcionalidad nueva cambie identidad visual, metadatos o datos curriculares fuera de su alcance.

## Fuentes de verdad

- Para el objetivo de una tarea: la solicitud actual del usuario y su archivo en `docs/tasks/`.
- Para el comportamiento existente: el codigo y las pruebas de la rama en la que se trabaja.
- Para decisiones estables compartidas: este archivo.
- Para el protocolo de trabajo, integracion y publicacion: `AGENTS.md`.
- Para la importacion y validacion curricular desde Bedelias: `docs/bedelias-importer.md`.
- El importador puede ejecutarse por plan, como lote secuencial y reanudable por servicio o como inventario global en seco; estos procesos locales no usan modelos ni APIs de IA y no publican datos automáticamente.

Si estas fuentes parecen incompatibles, el agente debe comprobar primero si su worktree quedo desactualizado respecto de `main`. No debe inventar una conciliacion ni copiar cambios desde otro worktree sin autorizacion.

## Comandos de verificacion

- `npm test`: compila y ejecuta la suite automatizada.
- `npm run test:unit`: ejecuta la suite Node sobre un `dist/` ya compilado; `npm run verify`: ejecuta lint, compila y luego corre la suite; `npm run package`: empaqueta el `dist/` verificado.
- `npm run lint`: valida el codigo fuente.
- `npm run dev`: inicia el entorno local para validacion funcional y visual.

## Reglas para mantener este contexto

- Leer el archivo completo al comienzo de cada tarea.
- Registrar solo hechos confirmados y decisiones duraderas que afecten a varias funcionalidades.
- No agregar planes temporales, tareas pendientes, conversaciones, nombres de chats, ramas, hashes de commits ni detalles exclusivos de una feature.
- Las especificaciones detalladas van en `docs/tasks/<nombre>.md`, un archivo por funcionalidad.
- Actualizar este documento en el mismo commit que cambie una decision transversal, una fuente de datos, la arquitectura, la persistencia o los comandos oficiales.
- Mantenerlo breve. Cuando un tema requiera detalle operativo, enlazar un documento especifico en `docs/` en lugar de copiarlo aqui.
- Durante la integracion final, revisar que el documento describa el estado combinado de `main`, no solamente el worktree de una funcionalidad.
